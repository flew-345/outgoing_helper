# 珞珈畅行 MVP 功能清单与技术方案

> 目标：为武汉大学师生提供一个整合校巴、共享电动车和道路管制信息的校园智能出行助手。

## 一、MVP 功能清单

### P0：首个可用版本必须完成

- [ ] **校园地点搜索与选择**
  - 支持宿舍区、教学楼、食堂、校门、校巴站点等常用地点。
  - 支持名称模糊搜索、起点终点互换和常用地点收藏。
- [ ] **步行路线规划**
  - 展示路线、距离、预计用时和沿途受影响路段。
- [ ] **校巴线路与站点查询**
  - 展示线路、站点顺序、运营时间和票价/乘坐说明（如适用）。
- [ ] **校巴移动信息**
  - 接入车辆位置或预计到站时间。
  - 没有实时接口时，明确展示“数据更新时间”和“实时状态不可用”。
- [ ] **道路与临时管制提醒**
  - 展示施工、封路、拥堵、樱花季、军训等临时管制。
  - 规划路线遇到管制时自动绕行，并说明绕行原因。
- [ ] **多方案比较**
  - 比较步行、校巴、共享电动车和组合方案。
  - 统一计算步行接驳、等车、乘车、找车、骑行和下车后的总耗时。
  - 给出推荐方案及可解释的推荐理由。
- [ ] **自然语言出行问答**
  - 支持“从桂园到银泰城怎么走”“现在适合等校巴还是骑车”等问题。
  - 回答必须引用当前查询到的路线、状态和管制数据，避免只生成泛化建议。
- [ ] **数据可信度标识**
  - 每条动态信息显示来源、更新时间和有效期。
  - 数据过期、缺失或冲突时，给出明确提示和可执行的备用方案。

### P1：完成闭环后优先增加

- [ ] **两类共享电动车统一展示**
  - 统一展示两家平台的车辆位置、可用数量、服务范围和停车点。
  - 标注数据来源与更新时间；暂不承诺账号、扫码和支付互通。
- [ ] **消息提醒**
  - 校巴临近到站、常用路线受影响、道路即将封闭等提醒。
- [ ] **管理员信息维护**
  - 管理员维护校巴线路、站点、管制区域、公告、生效时间和失效时间。
  - 支持信息审核、撤销和操作记录。
- [ ] **地图交互优化**
  - 路线图层、车辆图层、管制区域图层和图例。
  - 支持定位、缩放、路线详情和分享。

### P2：有稳定数据和合作授权后再做

- [ ] 两家共享电动车平台的账号互通、扫码开锁和支付。
- [ ] 全武汉公共交通和校外路线的统一规划。
- [ ] 基于历史数据的拥堵预测、到站预测和个性化推荐。
- [ ] 原生 iOS/Android 应用；MVP 先使用响应式 Web，降低交付成本。

## 二、MVP 验收标准

1. 用户输入一句自然语言，系统能识别起点和终点，并展示至少一个可执行路线。
2. 对同一地点，系统能比较步行、校巴和共享电动车方案，并显示总耗时、数据时间和推荐理由。
3. 新增一条有效封路或管制信息后，受影响路线会绕行，并在结果中说明原因。
4. 校巴或共享电动车数据缺失、过期时，系统不会伪装成实时状态，而是展示状态说明和替代方案。
5. 管理员可以录入、更新和失效一条管制信息，用户端能看到对应变化。

## 三、推荐技术栈

### 前端

- **框架：** Next.js + React + TypeScript
- **样式：** Tailwind CSS
- **地图：** 高德地图 JS API 或腾讯地图 API；优先选择能覆盖校园 POI、步行路线和驾车/骑行规划的服务。
- **数据请求：** TanStack Query
- **表单与校验：** React Hook Form + Zod
- **部署形态：** 响应式 Web，兼容手机浏览器和桌面端。

### 后端

- **框架：** NestJS + TypeScript，或 FastAPI + Python（二选一即可）。
- **接口：** REST API；实时车辆状态可在后续增加 WebSocket 或 SSE。
- **数据库：** PostgreSQL + PostGIS，存储地点、线路、站点、路线和空间管制区域。
- **缓存与任务：** Redis；定时同步校巴、电动车和公告数据。
- **后台管理：** 基于同一前端增加管理员路由，或使用轻量 CMS/管理模板。

### AI 与数据接入

- **大模型：** 选择具备函数调用能力的模型，让模型调用地点搜索、路线规划、校巴状态和管制查询工具。
- **智能体编排：** MVP 可使用后端自建工具调用流程；需要复杂多轮流程时再引入 LangGraph/LangChain。
- **知识库：** 校园规则、校巴说明和常见问答可放入向量检索；实时路线和车辆数据必须直接查询数据库或外部接口。
- **数据同步：** 为每个外部数据源建立适配器，统一转换为地点、车辆、线路、管制和更新时间字段。

### 工程与运维

- **版本管理：** Git + GitHub/GitLab。
- **测试：** Vitest/Jest（单元与接口测试）、Playwright（关键用户流程测试）。
- **质量检查：** ESLint、Prettier、TypeScript 严格模式。
- **部署：** 前端 Vercel/Cloudflare Pages，后端 Railway/Render/云服务器，数据库使用托管 PostgreSQL。
- **监控：** Sentry 加接口日志；记录外部数据源失败、数据延迟和 AI 工具调用失败。

## 四、实现难度评估

| 模块 | 难度 | 主要原因 | MVP 建议 |
|---|---|---|---|
| 地点搜索与基础步行规划 | 中 | 需要整理校园 POI 并接入地图路线 API | 先覆盖核心校区和常用地点 |
| 校巴线路与站点 | 中 | 静态线路容易，数据准确性需要维护 | 先做一条线路或一个片区 |
| 校巴实时移动信息 | 高 | 依赖车辆定位接口、授权和稳定性 | 没有接口时先做运营时段和演示数据标识 |
| 道路/临时管制 | 中 | 需要空间范围、有效期和后台维护 | 先做管理员手工录入 |
| 多方式最优路线 | 高 | 要综合等车、接驳、找车、管制和数据新鲜度 | 先做规则评分，不急于训练模型 |
| 两类电动车统一展示 | 高 | 依赖两家平台接口、授权和字段差异 | 先用模拟数据或单方真实数据验证界面 |
| 自然语言问答 | 中 | 工具调用和数据引用设计比聊天界面更关键 | 只开放受控的查询工具 |
| 消息提醒 | 中 | 需要任务调度、用户订阅和推送渠道 | 先做站内提醒，再接短信/小程序推送 |
| 账号、扫码、支付互通 | 极高 | 涉及平台合作、身份、支付和安全责任 | 明确排除在 MVP 之外 |

## 五、建议实施顺序

1. 整理校园地点、道路、校巴线路和管制数据模型。
2. 完成地点搜索、地图展示和步行路线。
3. 加入校巴线路、站点和静态运营信息。
4. 加入管制录入、有效期判断和路线绕行。
5. 实现步行/校巴/共享电动车的方案比较与推荐规则。
6. 接入自然语言工具调用，让问答复用已有查询能力。
7. 在取得授权后接入实时校巴和两类电动车数据。
8. 用真实场景完成端到端测试，再扩展提醒和后台能力。

## 六、关键风险与应对

- **实时数据拿不到：** 产品架构保留静态数据、手工维护和模拟数据入口，并始终标注数据状态。
- **地图路线与校园实际不一致：** 建立校园道路和禁行区域的人工校正机制。
- **AI 给出不可靠建议：** AI 只能调用受控工具；答案展示数据时间、来源和不确定性。
- **两家平台合作周期长：** 将统一展示设计成可插拔数据适配器，先完成不依赖合作的核心流程。
- **临时管制更新滞后：** 管制记录必须包含生效/失效时间，并支持管理员快速撤销。
